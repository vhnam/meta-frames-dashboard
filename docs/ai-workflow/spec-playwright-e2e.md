# Dashboard Playwright adoption and test plan

## Goal and scope

Catch failures that require a browser, the dashboard and the Go API to interact. The first release should answer two questions. Can a guest sign in and return to the requested page? Can a signed-in user change inventory and see the persisted result after reload?

The dashboard already tests Vue components, query invalidation, form rules and routing with Vite+, Vitest, happy-dom and a fake server. See `src/test/api.test.ts` and `src/features/auth/auth.test.ts`. Keep those fast checks. Use Playwright Test for cookies, credentialed cross-origin requests, deep links, browser history and writes visible through a fresh read. Exclude visual snapshots, exhaustive validation permutations, live Google sign-in and email delivery from the initial suite.

## Environment and test data

- Run the actual dashboard build and the actual Go API. Set `VITE_API_URL` **before** building. Preview the resulting assets on a fixed loopback port with strict port binding. Use the same hostname for both processes. Example origins are `http://127.0.0.1:4173` and `http://127.0.0.1:18080`. Set server `CORS_ORIGINS` and `APP_URL` to the dashboard origin. Axios sends cookies through `withCredentials`.
- Start a disposable PostgreSQL 18 instance per run and give the server its explicit DSN, port and temporary `STORAGE_DIR`. Start the server binary directly with test settings. The server applies migrations before listening. Its development Compose file fixes the container name, host port and volume. Reusing that stack could write to a developer's database. Tear down only resources created by the run, including after failure.
- In CI, obtain the compatible server revision explicitly and record both commit SHAs. A sibling checkout exists locally. A fresh CI checkout needs access to that repo or a versioned server image. Supply any read credential through the CI secret store. Keep the suite runnable locally while CI access is being arranged.
- Use Playwright's webServer readiness checks for the dashboard and API, including `/health`. Fail on an occupied test port in CI. Register unique accounts through the existing API. Seed prerequisites through authenticated requests. Drive the action under test through the UI and verify its effect after reload or an independent API read. [Web server configuration](https://playwright.dev/docs/test-webserver)
- Give every test a fresh browser context. Give mutating tests unique records and accounts, including on retries. Keep the login case anonymous at startup. For other cases, log in through the API in the browser context's request client so both use the same cookie jar. One account per test is sufficient at this scale. Exclude any saved auth state from Git and uploaded artifacts. [Authentication](https://playwright.dev/docs/auth)

## Authoring and failure policy

- Locate controls by role and accessible name, or by form label. Scope repeated controls to their dialog or record. Add a stable test ID only when semantics cannot distinguish the target. Assert persisted state, identity and navigation. Keep copy, headings, CSS classes and element order out of acceptance criteria. [Best practices](https://playwright.dev/docs/best-practices)
- Use locator actions and retrying assertions. Register response waits before the triggering click when the HTTP result matters. Use specific requests or visible state to detect completion. Fixed sleeps and global network-idle waits hide races. Keep the primary journeys on the real API. Use targeted routing only for a separately identified fault-injection case. [Best practices](https://playwright.dev/docs/best-practices)
- Start CI with one worker, zero local retries and at most one CI retry for diagnostics. Mark a retry-only pass as flaky and fail the PR gate on flaky results. Keep a failure trace from the first attempt, capture screenshots on failure and publish a restricted HTML report. Set a short artifact retention period because traces can contain cookies and submitted form values. [CI guidance](https://playwright.dev/docs/ci) · [Retries](https://playwright.dev/docs/test-retries)
- Debug one spec with Playwright UI mode or inspect its trace. Check the first failed request, browser origin, cookie state and backend logs before changing timeouts. Keep locators in the spec until repetition justifies a shared helper. A fresh run must reproduce a failure without depending on test order.
